# Provider audit and compatibility

Audited 8 October 2026 against local record shapes and public provider interfaces. Provider CLI installs and desktop apps are optional for reading saved local history. The scanners use read-only SQLite and bounded JSONL reads. They do not attach to a running agent runtime. These local schemas are version-dependent; a provider update can remove fields without making their missing values zero.

## Codex

- Available: `threads` index identity/title/model/provider, agent nickname/role/path, CLI version, creation/update times, token index totals and spawn edges with recorded statuses. Rollout startup metadata adds explicit parent, fork, depth and provider identity. Recent rollout records add last message, completion/interruption, model evidence and token breakdowns.
- Previously read: recent index rows, all spawn edges and a 128 KiB event tail, including legacy `event_msg.token_count.info.total_token_usage`. The tail frequently missed startup identity and newer token records.
- Now read/displayed: both legacy totals and `token_usage_record.thread_token_usage`; `turn_token_usage` is shown separately. Per-response `usage` is never relabelled a chat total. Cache read and reasoning remain subsets, not additions. Startup metadata is read separately and never replays old lifecycle/token events into recent state. Index/event disagreement is labelled rather than merged into a fabricated total. Creation, version, agent path/depth, model provenance and explicit fork lineage appear in Context. Spawn statuses remain historical relationship evidence.
- Normal scans cap edge reads at 4,000 and restrict them to loaded/requested threads. An unavailable related chat can be loaded by its exact index ID without increasing the history limit. Up to 32 temporary related-chat pins refresh with the normal scan. Archived/deleted records are unavailable through this action.
- The documented [app-server](https://learn.chatgpt.com/docs/app-server) offers `thread/read` without resuming, and paginated history interfaces (some experimental). A newly started server is not the owning runtime of another running chat; its `notLoaded` status does not establish that the other chat is inactive. Polling therefore does not spawn a server or repair provider data. Explicit archive actions use the app-server protocol; Codex may also archive spawned descendants, which the confirmation now states. No archive actions were exercised on existing chats for this change.
- Limits: no live control connection, bill, current context-window occupancy, remote-only worker discovery, or proof of task correctness. Shared/forked histories can overlap in recorded token totals. The file/database interface, including newer usage fields, is not promised as a stable external API.

## Claude Code

- Available: runtime registry, project index, main/parent-scoped subagent JSONL, and optional `agent-<id>.meta.json` sidecars. Sidecars observed in the installed version contain `agentType`, `description`, `spawnDepth` and sometimes requested `model`. Assistant messages record the actual model, usage and stop reason. Per-message streams can repeat IDs.
- Previously read: runtime PID/start identity, main and recent worker tails, model/usage, latest message and parent layout; worker sidecars were omitted. The app assumed Anthropic was the provider.
- Now read/displayed: sidecar role/task/depth and requested-model fallback, with an assistant model taking precedence. Recorded provider version and first observed file time are labelled. Claude billing provider is unknown because a Claude model can be served through multiple providers; no credentials/configuration are read to guess it. Worker IDs remain scoped to their parent. Parent navigation/resume stays separate from worker identity.
- Normal usage reads remain deduplicated 128 KiB tails. On-demand deeper reads cover up to 8 MiB and are labelled entire available transcript or partial tail. Duplicate message IDs count once using the maximum recorded counter per ID. Separately recorded cache read/write tokens are included once. If counter fields are absent, the summed available values are explicitly labelled a recorded subtotal; absent counters remain absent. A complete available file is not proof of complete provider/account history. Provider-owned `stats-cache.json` remains a dated overall snapshot, separate from chat counters.
- Limits: sidecars and runtime registries are implementation details, not documented portable APIs. Missing sidecars leave roles unknown. The [documented subagent interface](https://code.claude.com/docs/en/sub-agents) and [CLI resume interface](https://code.claude.com/docs/en/cli-reference) do not establish arbitrary live attachment to existing desktop workers. No per-chat bill is synthesized from model prices, and no current context occupancy is inferred. The Claude desktop route is optional/private and version-dependent; CLI resume is the fallback.

## Hermes

- Available: root and named-profile `state.db`; sessions include parent, start/end/reason, source, activity, model/billing provider, input/output/cache/reasoning and estimated/actual costs with cost status/source. Messages supply previews and finish reasons. Compression uses parent chains. Optional leases/active registries supply ownership/process evidence.
- Previously read: recent sessions, aggregate usage, messages, all lineage and leases; end/activity/cost-source fields were not exposed in Context, and child relations were generic.
- Now read/displayed: start/end, recorded outcome/activity and cost source; explicit `source=subagent` or stored `_delegate_from` children are distinguished from generic child sessions and compression continuations. Input + output excludes separately stored cache/reasoning fields. Actual and estimated costs stay separate; absent costs are unknown, while recorded zero remains zero. Named profiles retain independent identities and resume homes. Requested related IDs are loaded within their own profile. Optional message/lease schema changes no longer hide otherwise readable sessions. Lineage reads cover direct relationships and at most 32 ancestors, with 4,000-row query caps.
- The inspected [delegation implementation](https://github.com/NousResearch/hermes-agent/blob/main/tools/delegate_tool.py) persists child sessions when a parent database is available. Its richer plugin subagent lifecycle service exposes role/depth/outcome handles in-process; this app has no runtime bridge to that service. Persisted sessions do not reliably contain those live handles, so no live role/depth is fabricated. Gateway session APIs are not connected, and gateway processes are not auto-discovered/started.
- Limits: schema-dependent persistence may omit transient workers. Per-model/task buckets in `session_model_usage` and async-delivery records are not read in this version. Delegated workers can inherit a desktop/CLI source; the scanner selectively extracts only `_delegate_from` from bounded-size `model_config` JSON to recognize them, without loading other configuration fields. Only stored session counters are exposed; they must not be interpreted as invoice totals or complete runtime accounting.

## T3 Code V2

Inspected 23 October 2026 against the installed 0.1.2 desktop/server bundle and local V2 projection schema. The adapter is independent code; no T3 runtime code or private data is bundled.

- Reads `userdata/statev2.sqlite` (or `statev2.sqlite` when the selected folder is `userdata`) in a read-only transaction. Uses bounded thread/run projection payloads, per-thread indexed latest-message reads, pending request metadata and explicit lineage. It does not scan/replay the orchestration event log or read authentication tables/files. Message extraction selects user/assistant text only, up to 8,000 characters; tool output and secret contents are excluded.
- The active run takes precedence over a queued follow-up. Pending blocking user input, supported approval kinds and auth refresh map to different attention states. A pending private-input item is recognized by type/status for an active run, without reading its contents. Queued, interrupted, cancelled and rolled-back records are idle with recorded evidence; completed runs have one-completion review timestamps, and settled completions are idle. Stopped/reused server PIDs cannot establish live states: the runtime PID and UTC process start must match within the bounded startup interval. Without that evidence, active/pending records are Unknown; completed/failed history remains historical.
- V1 `state.sqlite` is deliberately not read when V2 is absent or empty. [T3 documents](https://github.com/pingdotgg/t3code/blob/main/docs/user/thread-migration.md) that migration copies the database once and subsequent histories diverge. Migrated/forked conversation history can be absent from local message projections until T3 imports it; missing text is not treated as an empty full conversation.
- Strong root-native thread references link loaded Codex/Claude records to exactly one loaded T3 owner (including T3's `claudeAgent` driver). Ambiguous, weak and provider-worker references do not hide a native record. The combined main list counts the host once; native records remain available through provider filters, bookmarks and Context. Native archive is disabled for a known hosted provider record; archive it in T3 instead.
- Consumption uses only persisted provider-turn `turnTokenUsage` with T3's normalized `usageScope=main_agent` and complete/partial status. The inspected `TurnTokenUsage` contract includes cache reads and writes inside input, and reasoning inside output, across providers. The chart removes those subsets before stacking. The separate `tokenUsage` and provider-thread `contextUsage` describe context occupancy and are never summed. Root provider turns are summed by durable turn identity; provider switches retain their separate turns. Missing/invalid/unavailable counters remain unknown, explicit zero is preserved, and incomplete turns, chats without counters and worker-bearing turns make coverage partial.
- The overall T3 usage card aggregates recorded main-chat turns across the local archive, including archived but excluding deleted chats, separate subagent chats and native worker provider threads. It is explicitly a hosting view that overlaps native-provider archive totals; those existing provider totals keep their scope and must not be added to the T3 bar. The seven-day session chart counts a measured T3 host and omits its exact matched native records. Without T3 consumption, native records remain a fallback; unmatched identities can still overlap. V1 imports and active turns may lack consumption. Per-session stats refresh with chat scans; overall aggregates use the existing one-minute cache and invalidate on a T3-home change.
- Native opening uses the installed app's `promptLinkAppPath` route `t3code://threads/<environment-id>/<thread-id>`. App-owned child chat lineage remains distinct from a fork. Related T3 chats can be requested by exact ID, subject to the existing 32-pin limit. Provider-thread reference reads cap at 4,000 and label incomplete relationship coverage.
- Limits: one configured local V2 environment; no remote environment discovery, V1-only support, sends, archive operations, task completion guarantee or full transcript rendering. These projection tables and desktop routes are version-dependent. Unknown schema is reported as unavailable rather than migrating or modifying T3 state.

## Bounded reads and saved history

Git/runtime JSON/transcript reads reject FIFOs and other non-regular files using nonblocking opens and file-type checks, so a named pipe cannot stall a refresh.

Normal transcript extraction is cached by provider, path, file size, modification time and read cap. Each changed transcript reads up to 128 KiB of startup metadata plus 128 KiB of recent events. Startup records larger than the cap or malformed/truncated lines may not be parsed; missing data stays unavailable. Selected deeper reads use at most 8 MiB of the tail plus the startup read, cache extracted metadata only, and retain at most 12 expanded detail results in the UI. A size/mtime change invalidates expanded results. Changing a file while it is read can give a partial snapshot; the next refresh retries discovery without provider mutations.

Stored bookmarks are historical snapshots. No saved preview proves live activity. Allowance windows are dated account/limit snapshots, separate from cumulative session and turn usage. No cross-provider, parent-plus-children, or context-occupancy total is computed.

## Fixtures

`Tests/SessionMonitorTests/Fixtures` contains hand-authored synthetic records and SQL, not exports of real conversations. They use `/example` paths, example model/provider names and fixture identities. Tests cover newer/legacy usage semantics, head/tail separation, bounded expanded reads and invalidation, worker sidecars, missing fields versus zero, continuations, per-profile lookup, schema drift, home/CLI overrides and compatibility with older saved annotations. No provider CLI, account or network access is required to run the tests after SwiftPM dependencies resolve.
